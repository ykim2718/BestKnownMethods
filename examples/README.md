# bkm examples

End-to-end walkthrough for the `bkm-generator` CLI and the `bkm` Python API,
using **synthetic wafer data** generated on the fly (no external data needed).

## Folder layout

```
examples/
├── README.md                       this file
├── 00_generate_sample_data.py      synthesize wafer parquet files
├── 01_run_training.py              CLI training (--update) + render PNGs
├── 02_run_inference.py             CLI inference (no --update)
├── 03_python_api_demo.py           build branched DAG via Python API + render
│
├── training_data/                  ┐  generated by 00 — 18 parquet wafers
│   ├── LOT01_WA00.parquet          │  (3 loaf patterns × 6 wafers each)
│   └── ...                         ┘
│
├── inference_data/                 ┐  generated by 00 — 5 parquet wafers
│   ├── LOT02_WA00.parquet          │  (3 known patterns + 2 novel "unknown")
│   └── ...                         ┘
│
└── bkm_results/                       ┐  generated by 01 / 03
    ├── bkm_directory.json          │  BKM versions (write: 01, read: 02 & 03)
    ├── bkm_wafers.json             │  wafer→BKM mapping (write: 01)
    └── diagrams/                   │  rendered DAGs (write: 01)
        ├── bkm0001.png / .mmd      │
        ├── bkm0002.png / .mmd      │
        └── bkm0003.png / .mmd      ┘
```

`training_data/`, `inference_data/`, and `bkm_results/` are recreated on every run.
They are not committed to the repository.

## Run order

From the **project root** (`bkm/`):

```bash
python examples/00_generate_sample_data.py
python examples/01_run_training.py
python examples/02_run_inference.py
python examples/03_python_api_demo.py
```

## Per-script I/O

| Script | Inputs (read) | Outputs (write) |
|---|---|---|
| `00_generate_sample_data.py` | (none — values are hard-coded `PATTERNS`) | `training_data/*.parquet`, `inference_data/*.parquet` |
| `01_run_training.py` | `training_data/*.parquet` | `bkm_results/bkm_directory.json`, `bkm_results/bkm_wafers.json`, `bkm_results/diagrams/bkm*.png` & `.mmd` |
| `02_run_inference.py` | `inference_data/*.parquet`, `bkm_results/bkm_directory.json` | (stdout only — assigns each wafer to a BKM, prints `unknown` for non-matches) |
| `03_python_api_demo.py` | `bkm_results/bkm_directory.json` (Part 2 inspect) | (stdout only — builds a branched BKM in-memory and prints registry inspection) |

> **`bkm_directory.json` is both an input and an output**, depending on which
> script touches it: `01` writes it (training, with `--update`); `02` and `03`
> read it (inference / inspection). `bkm_wafers.json` is write-only output
> from `01` (informational mapping; not consumed by inference).

## Input parquet schema

Each parquet file = **one wafer**, with one or more rows. All rows in a file
share the same `wafer_id` and `tkout_time`; the per-row
`equipment / chamber / chamber_step / sensor` values are combined into a single
**loaf** string by the generator.

| column         | dtype    | meaning                                |
|----------------|----------|----------------------------------------|
| `wafer_id`     | str      | wafer identifier (unique per file)     |
| `tkout_time`   | datetime | track-out timestamp                    |
| `equipment`    | str      | equipment id                           |
| `chamber`      | str      | chamber                                |
| `chamber_step` | str      | chamber step                           |
| `sensor`       | str      | sensor name                            |

Source of truth: column-name literals in
[src/bkm/generator.py](../src/bkm/generator.py) (`col_wafer_id`,
`col_tkout_time`, and the `BKM_COLUMNS_DEFAULT` list inside `parse_args()`).

## Training vs inference

| mode      | flag        | what happens                                         |
|-----------|-------------|------------------------------------------------------|
| training  | `--update`  | rebuild registry from scratch, write `bkm_directory.json` |
| inference | (none)      | load existing registry, assign each wafer to a known BKM or flag `unknown` |

## Linear vs branched DAGs

The CLI flow (`add_bkm_loaf` → one loaf string per wafer) only produces
**linear** DAGs of the form `in → loaf → out` — that's why `01_run_training.py`
gives 3 single-loaf BKMs.

To demonstrate a **branched** DAG (`in → loafA → {loafB, loafC} → out`),
`03_python_api_demo.py` builds `demo_v1` directly through the `BKM` constructor's
`process_data` parameter, bypassing `add_bkm_loaf`. Branched DAGs in production
typically come from `BKM.read_wafer_edges_from_df()` fed a multi-row, time-segmented
DataFrame (one row per loaf, each with its own `tkin_time`/`tkout_time`).

## Reading `bkm_results/` after a run

After `01_run_training.py` completes, `bkm_results/` looks like this:

```
bkm_results/
├── bkm_directory.json      ← BKM versions (the "registry")
├── bkm_wafers.json         ← which wafer was assigned to which BKM
└── diagrams/
    ├── bkm0001.png         ← Graphviz-rendered DAG
    ├── bkm0001.mmd         ← same DAG as Mermaid source
    └── ... (one pair per BKM version)
```

### `bkm_directory.json` — the BKM registry

Each top-level key is a BKM version. Excerpt for `bkm0001`:

```json
{
  "bkm0001": {
    "version": "bkm0001",
    "fingerprint": "67c45bf8e9985af9...",
    "labels": { "wafer_id": "wafer_id", "loaf": "loaf", ... },
    "nodes": {
      "in":                                  { "next_steps": ["eq1+eq2+ch1+ch2+cs1+cs2+se1+se2"] },
      "eq1+eq2+ch1+ch2+cs1+cs2+se1+se2":   { "next_steps": ["out"] },
      "out":                                 { "next_steps": [] }
    },
    "loaf_set": ["eq1+eq2+ch1+ch2+cs1+cs2+se1+se2"]
  },
  "bkm0002": { ... },
  "bkm0003": { ... }
}
```

| field | meaning |
|---|---|
| `version` | auto-generated id (`bkm0001`, `bkm0002`, …) |
| `fingerprint` | SHA-256 of the DAG structure — two BKMs with the same shape have the same fingerprint |
| `labels` | column-name labels used when this BKM was built (echoed back so loaders reconstruct the same `BKM` instance) |
| `nodes` | adjacency list — `{node: {"next_steps": [...]}}`; `in` is the source, `out` is the sink |
| `loaf_set` | sorted list of loaf names (excluding `in`/`out`); used as the matching key during inference |

**How to read a single version:** `in → <loaf> → out` if there's one loaf, or
follow the `next_steps` arrows to reconstruct the DAG. For `bkm0001` above:

```
in  →  eq1+eq2+ch1+ch2+cs1+cs2+se1+se2  →  out
```

The loaf string is decoded by **prefix**: `eq*` = equipment values, `ch*` =
chamber values, `cs*` = chamber_step values, `se*` = sensor values. Within each
column the unique values are sorted; **the order across columns matches
`--bkm_columns`** (default `equipment,chamber,chamber_step,sensor`). Changing
that CLI flag's order produces a different loaf and therefore a different BKM.

### `bkm_wafers.json` — wafer→BKM assignment

```json
{
  "LOT01_WA00": "bkm0001",
  "LOT01_WA01": "bkm0001",
  ...
  "LOT01_WC05": "bkm0003"
}
```

Flat `wafer_id → version` map. Use this to answer "which BKM does this wafer
belong to?" without reloading the registry.

> Inference (`02_run_inference.py`, no `--update`) does **not** rewrite either
> file — it only loads `bkm_directory.json`, prints assignments, and labels
> non-matching wafers as `unknown`. To regenerate `bkm_wafers.json`, rerun
> training.

### `diagrams/bkm*.png` — visualizations

Rendered with `BKM.render(fmt="png")` (Graphviz). Shape conventions:

- **Green pill** = `in`
- **Pink pill** = `out`
- **White rectangle** = single-successor loaf
- **Yellow rectangle** = branching loaf (more than one successor)

The matching `.mmd` file is the same DAG in Mermaid syntax — paste into
[mermaid.live](https://mermaid.live) or any Markdown viewer that renders Mermaid
to view as a different style.

### Quick interpretation cheat-sheet

| Question | Where to look |
|---|---|
| How many distinct BKMs were discovered? | count of top-level keys in `bkm_directory.json` |
| Which wafers map to BKM X? | filter `bkm_wafers.json` by value `"X"` |
| What does BKM X's process flow look like? | `bkm_results/diagrams/X.png` (or `nodes`/`loaf_set` in JSON) |
| Are two BKMs structurally equal? | compare their `fingerprint` fields |
| Which loaves does BKM X cover? | `loaf_set` field in its directory entry |
| Was a wafer unmatched? | run `02_run_inference.py` — `unknown` lines in stdout |
